# Stripe End-to-End Audit — 2026-05-13

Stripe is in LIVE mode (`sk_live_*`). Production payments table: 3 succeeded × $1,434.02 total (all `provider='manual'`, no Stripe charges have actually settled through automation yet). 3 active subscriptions, **all `amount_cents = 0`** (promo / free), none have a `stripe_*` id linked. 1 Connect account exists but **`charges_enabled=false`** and onboarding incomplete. That production state is critical: most of the lifecycle code below has **not been exercised in prod yet**. The first real paying customer will hit the bugs flagged here.

## MONEY-AT-RISK (P0)

### P0-1. Subscription webhook handlers query a column that does not exist — every renewal/cancel/past_due event is silently dropped

**Files**: `server/routes/payments.ts:322, 336, 355, 398, 403` and `server/routes/billing.ts:500, 514, 516`

**Schema reality** (verified via Supabase MCP — full `subscriptions` columns dump):
`id, user_id, plan_id, status, current_period_end, created_at, org_id, interval, currency, amount_cents, promo_code, referral_code, cancel_at_period_end, canceled_at, current_period_start, stripe_checkout_session_id, stripe_payment_intent_id, stripe_invoice_id, payment_confirmed_at, receipt_email_sent, receipt_email_sent_at, receipt_email_error`

There is **no `stripe_subscription_id` column**. Yet:

- `customer.subscription.updated` (payments.ts:322) — `.eq('stripe_subscription_id', sub.id)` → 0 rows matched, status never syncs.
- `customer.subscription.deleted` (payments.ts:336) — cancel from Stripe Dashboard never marks DB row canceled. **User keeps access after they cancel via Stripe.**
- `invoice.paid` (payments.ts:355) — `current_period_end` never advances on renewal. SaaS access window stale.
- `invoice.payment_failed` (payments.ts:398) — `past_due` never written. **Dunning is invisible.**
- `billing/cancel` (billing.ts:500/514/516) — Selects a column that doesn't exist. PostgREST returns a `42703` schema error → `subFetchErr` is truthy → route returns **500 "Failed to cancel subscription"** to the user. The Stripe-side cancel never runs. **A user who clicks Cancel sees an error AND keeps getting billed.** This contradicts the stated fix "Subscription cancellation was DB-only — fixed to call Stripe API" — the fix introduced a broken column reference.

**Severity**: Critical. With LIVE Stripe, the moment a real (non-promo) subscription is created via `mode: 'subscription'` Checkout (or even via `mode: 'payment'` if you later add recurring), Stripe will keep charging cards while our DB shows whatever state was set at activation. Refunds will pile up.

**Failure scenario**: Customer pays, Stripe sub renews next month, `invoice.paid` fires, our handler runs `.update().eq('stripe_subscription_id', sub.id)` → 0 rows → no error thrown (Supabase update silently matches 0). The webhook is marked "processed". Customer downgrades or cancels from their Stripe portal → `customer.subscription.deleted` → 0 rows → app still shows them as `active`.

**Fix**: add `stripe_subscription_id text` column to `public.subscriptions` (with a unique index), backfill from Stripe for the 3 existing rows (all have no real Stripe sub anyway since `amount_cents=0`), and also persist it in `handleCheckoutSessionCompleted` (payments.ts:1450 — currently only writes `stripe_checkout_session_id` and `stripe_payment_intent_id`, never the sub id).

### P0-2. Billing flow uses `mode: 'payment'` (one-shot) — there is no Stripe Subscription, no auto-renewal

**File**: `server/routes/billing.ts:656` — `mode: 'payment'`, line_items use inline `price_data` not `price`.

The webhook `handleCheckoutSessionCompleted` (payments.ts:1444) manually sets `current_period_end = now + 1 month` (or +1 year). Stripe will **never** charge the customer again. When `current_period_end` passes:
- No `invoice.paid` event ever fires (no Stripe subscription exists)
- The cron / access-gating logic must detect expired periods on its own. I see no such cron in `server/routes/cron.ts` or `reminders-cron.ts` that flips `subscriptions.status` to `expired` / `past_due` when `current_period_end < now()`.

**Result**: SaaS customers pay once, get a year of access, then `current_period_end` quietly expires and (probably) nothing happens — access continues forever, OR if access gating checks `current_period_end`, customer loses access with no renewal attempt and no email.

This is a fundamental product design decision masquerading as "subscription billing". Either:
1. Switch to `mode: 'subscription'` + real Stripe prices (proper recurring), OR
2. Keep one-shot but build a renewal-reminder cron that re-charges or emails the customer N days before `current_period_end`.

The audit context says "subscription model" but the code is one-shot. Flag and decide.

### P0-3. `handleCheckoutSessionCompleted` never persists the Stripe customer id or subscription id linkage needed for future webhooks

**File**: `server/routes/payments.ts:1450-1467`

`subscriptions` insert writes `stripe_checkout_session_id` + `stripe_payment_intent_id` but **not** any `stripe_customer_id` or `stripe_subscription_id`. `billing_profiles` (line 1487) does store `stripe_customer_id`. There's no link from a future `customer.subscription.*` event back to the org/subscription row — even if P0-1 is fixed, the cross-validation has nothing to match on.

### P0-4. `payments/refund` route uses the **platform** Stripe key for refunds — works only for destination charges; will fail or refund the wrong account for direct-charge payments

**File**: `server/routes/payments.ts:1265-1283`

```ts
const { getPlatformStripe } = await import('../lib/stripe-connect');
const stripe = getPlatformStripe();   // platform sk_live_*
...
refundParams.reverse_transfer = true;
```

This is correct for destination charges (`transfer_data.destination` is set, the platform's secret can refund and reverse the transfer in one call). **But** the quote-deposit Path-2 fallback (quotes.ts:1003-1044) creates `PaymentIntent` directly on the **org's own** Stripe account using the decrypted `stripe_secret_key_enc`. Those charges live on the org's Stripe account, not the platform's. A refund attempt through `/payments/refund` will fail with `No such payment_intent` (or worse — match a same-id intent on the platform account if Stripe ever reused the prefix, which they don't, but the error path leaves the DB marked refunded without actually refunding).

There is no branching on `payment.provider_account` / `payment.routing_mode`. The `payments` table has no column to tell us "this was a direct charge on org keys" vs "destination charge on platform".

**Fix**: add a `routing_mode` (or similar) column on `payments`, and pick the correct Stripe client (org-key decrypt vs platform) in the refund route. Also: `reverse_transfer: true` is a no-op (and silently ignored) on direct charges, but if the same code path were ever pointed at an org account the refund would attempt against the wrong account.

## Active bugs (P1)

### P1-1. `payments` table has no `disputed` or `partially_refunded` status enforced — `charge.refunded` and `charge.dispute.created` write strings the rest of the app may not know about

**Files**: `server/routes/payments.ts:421` (`partially_refunded`), `:445` (`disputed`)

No CHECK constraint on `payments.status` was found, so the writes succeed. But the refund route (line 1290) writes `'refunded'` for full and **keeps status as `'succeeded'`** for partial refunds — inconsistent with the webhook handler that writes `partially_refunded`. UI filtering will not group them coherently. Pick one convention and apply it.

Also: dispute handler updates `.eq('stripe_charge_id', chargeId)` but `stripe_charge_id` is never populated on insert (see `insertOrUpdatePaymentIdempotent` in lib/payments.ts:891 — only writes `provider_payment_id`, which is the *PaymentIntent* id, not the charge id). **Dispute webhooks will match zero rows.** Same problem for `charge.refunded` (line 425) — that one at least keys on `provider_payment_id = paymentIntentId`, so it works; but the dispute path is broken.

**Fix**: in `payment_intent.succeeded` handler, also persist `intent.latest_charge` into `payments.stripe_charge_id`.

### P1-2. Race condition on invoice `paid_cents` — read-modify-write, no row-level lock

**Files**: `server/routes/payments.ts:175-200, 362-381`; refund path 1299-1316.

```ts
const { data: invoice } = await admin.from('invoices').select('id, total_cents, paid_cents, balance_cents')...
const newPaidCents = Math.min(total, paid + amountPaid);
await admin.from('invoices').update({ paid_cents: newPaidCents })...
```

If two `payment_intent.succeeded` events arrive concurrently (e.g. retry storm, or two partial captures), both read the same `paid_cents`, both add their amount, the second write overwrites the first → **lost payment in `paid_cents`**, invoice shows underpaid, balance shows wrong, status may flip back to `partial`.

Mitigation today: Stripe webhook idempotency (event_id dedupe) protects against the *same* event arriving twice. It does **not** protect against two different intents settling simultaneously (e.g. deposit + balance, or two partial captures), which is a real scenario for invoices that take multiple payments.

**Fix**: use a Postgres SECURITY DEFINER RPC that does `UPDATE invoices SET paid_cents = paid_cents + $amt ... WHERE id = $id` in a single statement, or `SELECT ... FOR UPDATE` then update.

### P1-3. `charge.refunded` webhook does not decrement `invoices.paid_cents`

**File**: `server/routes/payments.ts:409-427`

It updates `payments.status` to `refunded`/`partially_refunded` but never touches the invoice. **Books are wrong** until the manual refund route is used (and only the manual route restores the invoice — line 1298-1316). A refund initiated from the Stripe Dashboard leaves `paid_cents` unchanged. The invoice stays `paid` while money was returned to the customer.

### P1-4. Webhook handler returns 200 even on processing errors → Stripe will never retry transient failures

**File**: `server/routes/payments.ts:469-477`

```ts
} catch (processingError: any) {
  if (webhookEventId) await markWebhookEventProcessed(webhookEventId, 'failed', ...);
  console.error('[webhook] processing error:', processingError?.message);
}
res.json({ received: true });   // always 200 unless signature fails
```

If the DB is briefly down or a transient timeout hits during `invoice.paid` processing, Stripe sees 200 and moves on. Our `webhook_events.status='failed'` is the only record. There's no retry job that scans `webhook_events WHERE status='failed'` and re-runs. **Funds reconciled in Stripe, never reflected in our DB.**

This is a deliberate trade-off (better than blocking the webhook), but at minimum a retry cron over `status='failed'` is needed. Right now: nothing.

### P1-5. PI creation lock in `public-pay` is correct, but quote-deposit (`quotes.ts:913`) has no such lock

A client double-clicking "Pay deposit" can create **two PaymentIntents** for the same deposit (different idempotency keys if the per-minute bucket flips at exactly the wrong moment, or just two simultaneous requests before either inserts). Both would settle, charging the customer twice. The deposit-confirm route checks `deposit_status === 'paid'` (line 1077) to short-circuit, but only on confirm — both charges would still settle on Stripe's side before either confirm runs. Refunding requires manual intervention.

**Fix**: same atomic lock pattern as public-pay.ts:183 (`UPDATE payment_requirements SET status='processing' WHERE status='pending' AND id=...`).

---

### P1-6. `public-pay` reuse of expired/canceled PaymentIntents has no failure mode

**File**: `server/routes/public-pay.ts:158-172`

If `paymentRequest.stripe_payment_intent_id` exists but the intent was canceled or succeeded by some out-of-band path, the code only reuses if status is in `['requires_payment_method', 'requires_confirmation', 'requires_action']`. For any other status (e.g. `canceled`, `succeeded`) it falls through to creating a new one — but the atomic lock right after (line 183) requires `status='pending'` and `is('stripe_payment_intent_id', null)`. Both fail → user gets 409 "already being processed" forever. **Dead end for that payment link.**

---

### P1-7. Onboarding-link refresh URL points to same handler — no rate limiting, no expiry guard

`server/routes/connect.ts:59-77` (`refresh-onboarding-link`) is literally a duplicate of `create-onboarding-link`. Both unconditionally call `accountLinks.create`. No abuse protection — an authed admin can spam this and generate dozens of single-use links. Low severity but worth noting.

## Edge cases not handled (P2)

### P2-1. No 3DS / `requires_action` handling on `/billing/subscribe`

`server/routes/billing.ts:274` — if `paymentIntent.status !== 'succeeded'` it returns 402 with the status. But for `requires_action` (3DS challenge required), the frontend needs `next_action` data to call `stripe.handleCardAction()`. The route currently returns `{ error, status }` — no `client_secret`, no `next_action`. **Cards in EU / many Canadian banks (Loi 13 SCA-equivalent) will silently fail.**

The Checkout-session path (`mode: 'payment'`) does handle 3DS because Stripe Checkout owns the flow — but the `/billing/subscribe` Elements path does not.

### P2-2. Currency hardcoded to CAD throughout fallbacks

- `payments.ts:159, 210, 268, 288` — `'CAD'` fallback in webhook intent processing.
- `lib/payments.ts:903` — payment insert default `'CAD'`.
- `public-pay.ts:217` — `paymentRequest.currency || 'CAD'`.

Most are reasonable fallbacks. The issue: there's **no validation that the org's connected account `default_currency` matches the invoice currency**. A CA-connected account cannot accept USD destination charges without conversion. No code checks this — Stripe will reject with a generic error at PI creation.

### P2-3. No tax handling anywhere — Stripe Tax not enabled

No reference to `automatic_tax`, `tax_code`, or `tax_id_collection` in Checkout / PaymentIntent creation. The receipt email (`server/lib/billing-email.ts` is referenced but not read) is passed `taxes: null` in both billing.ts:406 and payments.ts:1568. Compliance issue for QC/CA (TPS/TVQ) and US states. Hardcoded `tax_cents` in quotes/invoices is org-managed manually. Flag for Loi 25 / tax-compliance gap.

### P2-4. No trial period support

No `trial_period_days` anywhere, no `trialing` status handling in cancel flow. Promo codes set `amountCents = 0` and the subscription is just created `active`. The first 3 active subscriptions in prod are all `amount_cents=0`. There's no concept of "expires after free trial".

### P2-5. PayPal — env vars likely unset in prod

`server/routes/payments.ts:1198` (`PAYPAL_CLIENT_ID || PAYPAL_SECRET || paypalWebhookId`) returns 503 if missing — that's fine. But `lib/payments.ts:947` (`getPayPalAccessToken`) is called from PayPal webhook verification (line 1057) **before** the org-specific credentials check — falls back to platform env vars. If those are unset, webhook signature verification returns `false` for all PayPal events → all PayPal payments fail to reconcile silently. Need to confirm prod env. Per audit context: assume PayPal env unset → **all PayPal flows return 503 at create-order time, webhooks silently reject**. Document but not P0 if no one is using PayPal.

### P2-6. `deposit-confirm` uses `orgSecrets.stripe_secret_key_enc` directly without decrypting

**File**: `server/routes/quotes.ts:1096`

```ts
const orgStripe = new Stripe(orgSecrets.stripe_secret_key_enc);   // ← passing ENCRYPTED ciphertext as key
```

The `deposit-intent` path (line 1009) correctly calls `decryptSecret()`. The `deposit-confirm` fallback path does not. Result: Stripe SDK constructor accepts any string, but the API call will 401 (invalid key). The fallback exists for cases where the intent was created on org keys but `STRIPE_SECRET_KEY` (platform) is what's tried first — which is the common case for Path-2 (org-key) flow. **Deposit confirmations on org-Stripe path will fail.** Customer pays, sees error, retry stuck on `deposit_status='pending'`.

### P2-7. `process.env.STRIPE_PUBLISHABLE_KEY` leaked to public payment pages even when the org has its own keys

`public-pay.ts:169, 243` and `quotes.ts:988` — when using destination charges, the public payment page is told the **platform's** publishable key. That's correct for destination charges (PI lives on platform). But there's no defense against an attacker getting the platform pk and (combined with leaked metadata) trying to call Stripe.js with it. Stripe pk is meant to be public, so this is informational only — just confirm `STRIPE_PUBLISHABLE_KEY` in prod is the LIVE publishable, not a secret-by-mistake.

### P2-8. Application fee — only set for destination charges, not org-key direct charges

`lib/stripe-connect.ts:115` defines `APPLICATION_FEE_PERCENT = 2.9`. Used only in `createDestinationPaymentIntent`. When the deposit falls through to **PATH 2** (org's own Stripe keys, quotes.ts:1028), **no application fee is collected — Lume earns nothing on those deposits**. This is a business-logic gap, not a bug: with Connect-onboarded orgs, Lume gets 2.9%; with BYO-key orgs, Lume gets 0%. Was that intentional? Probably not — flag for product decision.

### P2-9. Webhook `event.created` age check is 5 min, but Stripe retries can come hours later

`payments.ts:107` rejects events older than 300s. **Stripe retries on 5xx for up to 3 days.** If we ever return 5xx (currently impossible due to P1-4), the retry would arrive >5min later and be rejected. Combined with P1-4 (no 5xx, no retry), this is moot — but as soon as you fix P1-4, the 5-min cap blocks legitimate retries. Either raise to 24h or drop the cap.

## Verified working

- Webhook signature verification (constructEvent with `STRIPE_WEBHOOK_SECRET`) — payments.ts:91. Failures logged with `critical` severity. Good.
- Idempotency via `webhook_events.stripe_event_id` unique constraint + early-exit (stripe-connect.ts:171-181). Race-safe via 23505 fallback. Good.
- Destination-charge routing for quote deposits (quotes.ts:975-989) — correctly uses `transfer_data.destination` to route funds to the org. Earlier audit's bug ("deposits going to platform") is genuinely fixed.
- Cross-org metadata validation on invoice updates (payments.ts:199-200) — scope by `org_id` defends against metadata tampering. Good.
- Refund idempotency key (`refund-${payment.id}-${amount}`, payments.ts:1282). Stripe idempotency window is 24h. Good for double-click protection.
- PCI scope: no raw card numbers in `git grep`-able server code. All card collection goes through Stripe.js / Checkout. `PAYMENTS_ENCRYPTION_KEY` used only for encrypting per-org Stripe secret keys at rest (lib/payments.ts:232). Confirm no `console.log(intent)` leaking PII — quick scan shows only ids logged, not full intents.
- Server-side amount calculation for quote deposits (quotes.ts:936-942) — never trusts client.
- Atomic PI-creation lock in public-pay.ts:183 prevents concurrent PI creation per payment_request.
- `Math.round(intent.amount_received || intent.amount || 0)` everywhere — no floating-point drift on cent conversion. Good.
- Email verification gate before checkout (billing.ts:178-184, :595-602) — prevents typo-email payments. Good.
- `processed_checkout_sessions` dedupe (payments.ts:1352) prevents duplicate org/user creation on webhook replay. Good.

## Summary of recommended fix order

1. **Add `stripe_subscription_id text` column to `subscriptions`** (and `stripe_customer_id`, and a `routing_mode` column). Persist them in `handleCheckoutSessionCompleted` and on org-direct payments. This single migration unblocks P0-1, P0-3, and enables P0-4.
2. **Decide subscription model** (P0-2): one-shot + renewal cron, OR migrate to `mode: 'subscription'`. Today's flow is neither.
3. **Persist `stripe_charge_id`** in `insertOrUpdatePaymentIdempotent` so the dispute handler (P1-1) actually matches.
4. **Atomic `paid_cents` update** via RPC (P1-2). Also have refund route and `charge.refunded` webhook decrement it (P1-3).
5. **Webhook retry cron** scanning `webhook_events WHERE status='failed'` (P1-4), and raise the event-age cap.
6. **Fix `decryptSecret` call in deposit-confirm fallback** (quotes.ts:1096) — P2-6.
7. **3DS handling** in `/billing/subscribe` (P2-1) — return client_secret + next_action.
8. Add atomic lock to quote-deposit-intent (P1-5).

Money-at-risk priority: P0-1 (cancellation broken — recurring charges continue after cancel UI says it failed) is the most urgent if any non-promo subscription exists or is about to. Currently all 3 prod subs are $0/free, so the bomb has not gone off — but the next real customer triggers it.
